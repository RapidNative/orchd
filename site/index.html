RapidNative Cloud
One orchestrator,
two products, one codebase

A multi-tenant workload orchestrator that powers both tinbase-cloud (hosted, Supabase-compatible backends) and RapidNative dev environments (per-project runners). Both are just workloads: containers it provisions, routes by subdomain, isolates with gVisor, and scales to zero when idle.

Powers: tinbase-cloud + RapidNative Isolation: gVisor Wake: ~0.9 s Idle RAM: 0 Control plane: Go

What it is

One substrate, two products

Both products need the same thing: run many small, per-tenant workloads cheaply, give each a subdomain, wake it fast, sleep it when idle, and isolate it well enough to run untrusted user code. So it is one orchestrator with a generic Workload primitive, not two.

tinbase-cloud

Hosted, Supabase-compatible backends. tinbase speaks the Supabase wire protocol, so @supabase/supabase-js works unchanged, but it is one ~66 MB process instead of a twelve-container stack. Coupled one-per-project like Supabase Cloud, at a fraction of the footprint. That density is the cost advantage.

RapidNative dev environments

The per-project runners behind RapidNative: a web/expo runner, a web/react runner, a dev tinbase, an api server, each on its own subdomain. They run untrusted user code and mostly sit idle, which is exactly what gVisor isolation and scale-to-zero are for.

The only difference between the two is the image and the routing. Everything else, provisioning, subdomains, waking, sleeping, isolation, is shared.

Architecture

Control plane, gateway, data plane

Everything above the runtime driver is substrate-agnostic. The control plane never talks to a VMM directly, it talks to a Runtime interface, so the substrate is swappable without touching anything above it.

Data model

Project → Workload → Route

Project

A logical grouping / tenant. Ownership and, later, billing live here.

Workload

The routable, independently-scheduled, scale-to-zero unit. The runtime lifecycle is keyed by workload id.

Route

A hostname mapped to a workload via an exact-match route table. Convention subdomains and custom domains resolve the same way; a workload can have many routes.

A plain tinbase project is one project, one primary workload, one route <ref>.<base>. A RapidNative project is one project with many workloads, each its own isolated instance on its own subdomain:

Why gVisor
It gives VM-grade isolation for untrusted code without nested virtualization, so it runs on a plain Cloud VM. A tenant container runs a gVisor userspace kernel, not the host kernel. Firecracker and Kata need /dev/kvm and therefore a dedicated bare-metal box, which is the future speed tier: per-project memory snapshot and sub-second resume.

Lifecycle

Scale to zero, wake on request

  1. Provision. The control plane mints a JWT secret and anon/service keys, allocates a volume, assigns a route, and boots the instance.
  2. Serve. Requests to the workload's hostname are proxied straight through to the running instance.
  3. Idle. After an idle timeout the instance is suspended (its container stopped): memory is freed, the volume stays at rest.
  4. Wake. The next request hits the gateway, which resumes the instance, then proxies. Data is exactly where it was.

Scale

Cost tracks warm projects, not total projects

Disk

The workload image (cache baked in) is content-addressed and layer-shared by Docker's overlay2, so it is stored once no matter how many containers run it. Per-project disk is just the data volume (~40 MB fresh). Long-idle data can be tiered to object storage and restored on wake.

Memory

Scale-to-zero means an idle project holds a stopped container and 0 RAM. Runtime memory tracks concurrently warm instances. Per-container cgroup limits keep packing predictable; add nodes when the concurrency ceiling is hit.
